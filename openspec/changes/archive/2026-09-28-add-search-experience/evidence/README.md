# add-search-experience — browser evidence (task 8.3)

Dependency-free Chrome DevTools Protocol harness that drives a real Chromium-based
browser against a production build of Spotivibe and verifies the M5 search
experience end to end: top-bar focus, URL-authoritative query state, stale-response
ordering, playback with navigation persistence, no autoplay on deep links, result
context menus + liking, search history, the zero-result empty state, offline
local-library fallback, and a zero-console-error run with screenshots.

All artifacts in this directory are generated by `cdp-check.mjs`. Evidence
directory is append-only output for this change; nothing here ships in the app.

## Reproduce

```powershell
# 1. Build the production bundle (required — the harness runs against `next start`)
cd frontend
npm run build

# 2. Serve it on the expected origin (leave this terminal running)
$env:PORT='3210'; npm run start

# 3. From the repository root, in another terminal
node openspec/changes/archive/2026-09-28-add-search-experience/evidence/cdp-check.mjs

# 4. Stop the server (Ctrl+C in terminal 2), or:
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -like '*next start*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId }
```

Optional environment overrides:

- `SPOTIVIBE_ORIGIN` — app origin (default `http://localhost:3210`).
- `SPOTIVIBE_BROWSER_PATH` — explicit Chromium/Edge executable.
- `SPOTIVIBE_CDP_PORT` — remote-debugging port (default `9445`).

The harness launches its own browser instance with a fresh temporary profile,
attaches over CDP, and kills that browser when it finishes (including on
failure), so no browser process is left behind. Exit code is `0` only when every
step passes; any failed step exits `1` with `"pass": false` in `results.json`.

## Findings

**Finding 1 — step 7 uses a CDP response stub, and why.** A genuinely
zero-track *remote* search response is unreachable against live providers:
YouTube Music Innertube returns fuzzy matches for any query (probes:
`zzqqxxyy12345unique`, `qzqxz1zqxz9f0zzq`, `xq9z7xq9z7w3v8b2` each returned 1–2
tracks), and when every provider is empty the API responds `503`
(`frontend/src/server/music/chain.ts` reports `ok: false`, surfaced as a
structured error by `frontend/src/app/api/search/route.ts`) rather than `200`
with `tracks: []`. The app's real "no results" branch therefore cannot be
reached through the live API alone. The harness uses the CDP `Fetch` domain to
fulfill exactly the one search request for the nonsense query with a synthetic
`200 {"tracks":[]}` body (all other requests pass through untouched, and any
stub error is recorded in `notes.fetchErrors`), then asserts the rendered empty
state. The live-provider behavior of that same query is recorded in
`notes.remoteEmptyState` (`fuzzyRemoteResult=true`, 2 tracks). This is a
harness-level boundary stub, disclosed here and in the step name — not an app
defect. If product requirements later dictate `200 {tracks: []}` for
all-empty provider chains, step 7 should be re-run against the live API.

**Finding 2 — hydration gating.** `next start` serves HTML that hydrates
asynchronously, so post-navigation assertions sample the document only after a
fresh document stamp (`window.__docStamp` from the fetch-spy script) plus a
hydration marker (`__reactProps$` on the focused input, or the player dock).
Both reload-based checks (steps 6) confirm `hydrated=true` before asserting.

**Finding 3 — offline is emulated, not physically disconnected.** Step 8 uses
CDP network emulation (`emulateNetworkConditions` with
`offline: true, latency: 0, downloadThroughput/uploadThroughput: 0`), which flips
`navigator.onLine` and makes the page issue no requests; physical Wi-Fi was not
toggled. `notes.requestsDuringOffline=0` proves the fallback rendered without
touching the network.

## What this run does NOT prove

- Non-Chromium browsers (Firefox/Safari) — only Edge/Chromium 154 was driven.
- Real network loss, flaky/high-latency conditions, or retry behavior beyond the
  emulated offline window.
- YouTube Music playback with sound, ads, age-restricted or live content, or the
  one-chunk-start guarantee (covered by M4 evidence, not re-asserted here).
- Playlist/artist/album navigation targets beyond opening the menu entries'
  presence (the menu items are asserted; the destination pages are M7/M9 scope).
- Mobile viewport/touch behavior (1280px desktop only).
- Long-run stability; this is a single scripted pass.
